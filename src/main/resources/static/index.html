POST /store/stock?productId=…

Остатки

—
Ручки GET /store/stock нет — таблица собирается из витрины GET /brand/{brandId}/products (brandId берётся из токена магазина) и отфильтрована по своему storeId. Удаление — DELETE /store/stock/product/{productId}.

Статус заказа

Обычно эти запросы шлёт partner-store на :8081 — он получает пуш об оплате и сам двигает заказ по таймеру. Здесь то же самое руками, чтобы видеть ручку вживую.

PATCH /store/order/{orderId} — заказ ищется по паре (orderId, storeId из токена), чужой заказ даст 404. Разрешена только цепочка PENDING→ACCEPTED→PREPARING→READY, шаг через ступеньку — 400, повтор того же статуса — 200.

Что реально есть в API

Собрано по контроллерам ветки refactor/store-model. Context-path — /api/v1, все ответы завёрнуты в ApiResponse { success, data, error, stats }, поэтому в таблице указано содержимое data.

Чего не хватает на бэкенде

Всё, что помечено demo на странице, работает на локальных заглушках, потому что ручки нет или она сломана. Зелёным — то, что закрыто с прошлого прохода.

Лог запросов

Страница лежит в src/main/resources/static/index.html и раздаётся самим Spring — открывай http://localhost:8080/api/v1/, тогда нет проблем с CORS. Если открыть файл напрямую (file://), браузер зарубит все запросы: CORS в проекте не настроен.

После вебхука заказ уезжает в partner-store (docker compose up -d partner-store, порт 8081) — отдельное приложение, имитация кассы магазина. Оно получает POST /orders и само дёргает PATCH /store/order/{id} по таймеру: ACCEPTED через 5 с, PREPARING через 15 с, READY через 30 с. Смотреть — docker compose logs -f partner-store.
